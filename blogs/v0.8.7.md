# JishuShell更新日志 | v0.8.7

---

JishuShell v0.8.7 正式发布。本次更新的核心，是把本地知识能力升级为一套**可验证、可管理的 JishuDB 托管链路**：JishuDB v0.5.1 作为新的内置知识服务加入，Core 会校验服务版本、接口与工具契约，再把经过约束的 MCP 工具交给 OpenClaw。与此同时，本次也集中修复了本机 Ollama 连接、模型选择、流式请求中断，以及 SearXNG、飞书/Lark 插件和 OpenClaw 自更新中的多项稳定性问题。

---

## 重点更新：JishuDB 成为内置托管知识服务

### 本地检索、管理界面与 MCP 一体化

JishuDB v0.5.1 现已作为内置 AppSpec 提供，集成 BM25、向量检索与 cross-encoder rerank，并同时提供 Web UI、HTTP API 和原生远程 MCP。安装后，JishuShell 会创建并验证默认知识库，完成服务鉴权和运行时配置，OpenClaw 可以直接使用已经连接的知识内容回答问题。

为保证每次安装得到一致的运行结果，内置镜像不再跟随可变的 `latest`，而是固定到经过验证的版本与镜像摘要。JishuShell 还会核对 JishuDB 的发布来源、服务版本、接口能力和完整工具 schema；运行中的服务与随 Core 发布的契约不一致时，连接会明确失败，而不是带着不确定的工具定义继续运行。

JishuDB 的访问令牌由 Core 生成并通过 Nomad Variables 注入，不写入普通运行时环境或 Agent 配置。启动、修复和并发更新共用受保护的状态写入流程，降低凭据泄露、半写入配置和多进程互相覆盖的风险。

> 当前内置 JishuDB 模板面向 Linux/arm64 设备（包括 Raspberry Pi）。不兼容的平台会在安装前返回明确提示，不会进入无法运行的安装流程。

### 知识文档上传契约补齐

Core 现在能够从 JishuDB 的认证能力接口读取可上传格式与可索引格式，并在连接期间验证这两组声明。PDF、Office 文档、Markdown、纯文本和常见图片等内容可以通过统一文档入口交给知识服务；实际可索引范围以当前 JishuDB 实例返回的能力为准，服务只支持其中一部分格式时也能正确协商，不再要求两份格式列表完全相同。

文档创建、列表、删除和标识符都经过统一约束，并支持保留来源路径、来源网址、批次与外部资源关联等元数据，为后续同步、追踪和去重提供稳定基础。

## 重点更新：OpenClaw 动态接入知识工具

### 工具随服务契约发现，不再依赖硬编码清单

OpenClaw 的知识连接现在由 Core 对 JishuDB 执行认证发现：先协商双方支持的 MCP wire protocol，再校验工具名称、输入输出 schema、服务数据版本和 streamable HTTP 响应能力，最后才写入 OpenClaw 配置。工具目录来自运行中的服务，并与随 Core 发布的固定契约核对，减少因名称、schema 或协议漂移导致的连接失败。

直接交给 OpenClaw 的仍然是最小安全工具集，默认只包含列出知识库、浏览文档、检索与读取内容所需的工具，不把创建、删除等管理操作一并开放给 Agent。知识契约发生不兼容变化时，JishuShell 会轮换旧会话状态，避免已有会话继续保留已经失效的工具说明。

这套流程还会在提交前后重复检查 provider、端点、凭据和工具目录；如果用户在连接过程中切换或重建了知识服务，旧事务会停止并回滚自己写入的临时凭据，不会覆盖新的有效连接。

### 旧知识产品契约正式退出运行路径

本版本移除了已经退役的知识产品模板、专用代理改写器、集成代码与 OpenClaw 适配路径，运行时只接受新的 JishuDB 托管契约。这样可以避免同一类知识能力同时经过多套兼容逻辑，也让后续升级只围绕一个明确的协议边界演进。

旧知识实例不会在升级时被静默改写成 JishuDB。若需要延续其中的资料，请先在原实例中完成备份或导出，再安装 JishuDB 并重新导入；不要直接改名、复制或链接旧数据目录给新实例。

## 重点更新：系统 Ollama 与模型连接更可靠

### 连接时真正采用所选模型

通过 Connections 为 OpenClaw 选择本机 Ollama 或其他 LLM provider 时，JishuShell 现在会保留并应用用户明确选择的模型。连接会验证目标模型确实出现在 provider 当前返回的模型列表中；未指定时，优先沿用仍然有效的原选择，再回退到第一个可用模型，避免配置页面选了一个模型、实际运行却仍使用占位值或旧模型。

对于 JishuShell 自动发现的系统 Ollama，Core 会重新探测本机服务、核对完整 registry 记录，并确认代理能够返回非空模型列表后才允许绑定。容器看到的连接地址与 Core 自己执行请求的回环地址也已分离，解决 macOS 等环境中 `host.docker.internal` 对容器可用、对宿主进程却不可解析的问题。

实例每次启动前都会根据已保存的连接重新对账派生配置，但不会擅自改选 provider。这样即使运行时配置曾被旧版本写错，重启也能恢复到当前连接事实与模型选择。

### 流式请求中断及时收尾

本次补齐了系统 Ollama 与通用 LLM 代理在客户端断开时的取消处理，覆盖响应头返回前、SSE 流传输中和上游清理阶段。浏览器关闭页面、切换会话或主动停止生成后，Core 会尽快取消上游请求并释放 reader，不再让中断的生成继续占用连接，也不会把正常的客户端取消误记为 provider 故障或触发错误的熔断统计。

## 重点更新：OpenClaw 插件与自更新修复

### 飞书/Lark 更新可自动恢复

部分 OpenClaw 与官方 Lark 插件版本组合中，npm 包已经包含可用入口文件，但 `package.json` 仍指向未发布的 `dist` 目录，导致控制面板升级在最后的插件检查阶段失败。本版本会只针对这个已知的缺失入口进行兼容修复，并继续执行 OpenClaw 自带的 update repair；修复成功后再由 JishuShell 重启和验证实例。

插件检测也已兼容 OpenClaw 新旧两种 npm 安装布局，包括新版按插件隔离的项目目录。保存飞书配置时，JishuShell 会识别已经安装的官方 Lark 插件，停用冲突的旧飞书插件入口，避免同一渠道被重复加载或让 Gateway 因插件冲突启动失败。

### SearXNG 连接可用性补齐

绑定 SearXNG 后，JishuShell 现在会同步维护 OpenClaw 的插件 allowlist，并在容器启动前幂等确认官方 SearXNG 插件已经安装。解绑时则清理 allowlist 与旧地址，避免配置看似已经连接、实际工具却因插件未加载而不可用。

## 更多改进

- **非默认端口更准确**：独立 CLI 命令启动时会优先读取显式环境配置或 Core 的持久化端口，LLM 代理与 Nomad 操作不再错误回落到默认端口。
- **安装状态更真实**：Dashboard 的 setup 状态现在从规范实例与实际生命周期状态判断 OpenClaw 是否运行，不再把已运行实例固定显示为未运行。
- **连接失败更可解释**：知识服务不可用、存在多个候选、契约不支持或绑定发生漂移时，会返回稳定的错误类型，便于界面和自动化给出准确提示。
- **并发写入更安全**：知识绑定、凭据与运行时状态增加跨进程锁、所有权校验和原子写入，异常退出后可以识别并回收过期锁，同时对损坏状态保持失败关闭。
- **静态资源依赖更新**：`@fastify/static` 已升级到 v10 系列，静态资源服务继续使用受支持的依赖链。

**升级方式：**

```bash
npm install -g jishushell@0.8.7
```

或通过 Dashboard 顶部的版本更新横幅一键升级。

如果你是**系统级安装**（已注册 systemd / launchd 服务），`npm install` 只会刷新包文件与 CLI / 面板启动脚本，并不会自动重启服务或对账实例。安装完成后，请按终端中的 `ACTION REQUIRED` 提示执行：

```bash
sudo jishushell repair
```

若 sudo 找不到命令，请使用提示中给出的绝对路径，例如 `sudo ~/.jishushell/bin/jishushell repair`。`repair` 会对账 Core、Nomad 与现有实例，并补齐本版本所需的运行时配置；它不会自动把旧知识实例转换为 JishuDB。完成后刷新已打开的 JishuShell 浏览器标签页即可。

> 普通的 `npm install -g jishushell`（非系统级服务安装）不会出现这一步，包文件刷新后即可直接使用。
